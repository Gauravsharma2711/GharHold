# ADR-001: Local-First Persistence, Outbox Pattern, Idempotency, and Optimistic Concurrency

## Status
Accepted

## Context
In Mumbai's hyper-competitive rental market, renters frequently experience "ghost availability" (listings advertised as vacant that have already been leased or promised) and double-commitment collisions. Mobile networks frequently experience intermittent drops during transit. If an application requires a synchronous remote server roundtrip before displaying state or confirming viewing holds, renters suffer duplicate submissions, lost records, and inconsistent UI states.

## Decision
1. **SQLite via Drift as Single Source of Truth**: All screens (GH01–GH07) observe reactive Drift database streams. The local database is the authoritative source of truth.
2. **Local Commit Before Remote Dispatch**: When a user submits an action, the domain invariants are validated, and the state transition is committed locally inside an atomic SQLite transaction (`REQUESTED` + `PENDING_SYNC` + `VIEWING_REQUESTED` + `STATE_TRANSITION` audit event) *before* attempting remote synchronization.
3. **Partial Unique Database Index**: To enforce the invariant that at most one active request exists per listing at all times, a partial unique index `one_active_request_per_listing` is created on `requests(listing_id)` filtering by `status IN ('REQUESTED', 'APPROVED', 'REOPENED', 'TOKEN_REQUESTED', 'TOKEN_CONFIRMED')`. The SQL is generated dynamically from the domain's `activeRequestStatuses` set.
4. **Idempotency Keys**: Every request generates a UUID `idempotencyKey` once on initial creation. Retries strictly reuse the existing key, preventing duplicate rows or holds.
5. **Optimistic Version Checks & Conflict Reconciliation**: Remote calls carry the `clientListingVersion`. If the server listing has incremented (e.g., to version 2 `UNAVAILABLE`), the client transactionally updates its local listing to the authoritative state, marks the request `ABORTED` with `CONFLICT_STALE_DATA`, and logs a `CONFLICT` audit event.
6. **Interrupted Startup Recovery**: On app launch, a startup recovery scan queries for any leftover `PENDING_SYNC` requests (indicating an app termination before remote sync completion), converts them to `SYNC_FAILED_RETRYABLE`, and logs a `RESUME_SCAN` audit event. The app never auto-sends requests without user awareness.

## Alternatives Considered
- **Direct Remote-First API (Synchronous HTTP)**: Discarded because network drops in Mumbai transit cause spinners, dropped requests, and accidental double-taps creating duplicate requests.
- **Client-Side In-Memory Cache Only**: Discarded because terminating or restarting the app loses all active viewing and token requests.
- **Generic Database Sync Engine (e.g. CouchDB/WatermelonDB/Firebase)**: Discarded as unnecessary complexity for the hackathon prototype; violates the cloud-independent local constraint.

## Consequences & Limitations
- **Consequences**: Fast, instantaneous UI responsiveness; guaranteed offline survivability; complete auditability of state changes; zero duplicate requests on retry.
- **Limitations**: In this prototype, remote sync is simulated locally via `SimulatedRemoteService`. Multi-device distributed sync requires future backend coordination services.
